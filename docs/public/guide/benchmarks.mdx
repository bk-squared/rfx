For validation scope and recommended engineering checks, read
[Cross-Validation and Accuracy](/rfx/guide/validation/).

`validation/crossval/manifest.json` defines the case list, dependencies, exit
codes, checks, and saved artifacts. Automated tests compare the table below
with that manifest, so a case cannot be added or reclassified without a
documentation update.

<Aside type="note" title="Pass criteria are case-specific">
  The metrics and tolerances below come from each script's docstring and check
  block. A pass applies to the stated geometry, mesh, frequency range, and
  reference only. It does not by itself validate other geometries, arbitrary
  discretizations, or an entire port or component family.
</Aside>

<Aside type="caution" title="Conductor cases are recomputed at 2.0">
  Release 2.0 changed how a conductor lands on the lattice: a PEC volume
  realizes walls at both of its drawn faces, and foil is declared as a sheet on
  one node plane
  ([How conductors land on the lattice](/rfx/guide/materials-geometry/#how-conductors-land-on-the-lattice)).
  Every case below with a declared conductor body — `05`, `07`, `11`,
  `15`, `18`, `19`, `20` — is re-solved from the drawn geometry, with the
  compensations that used to sit in its oracle deleted rather than re-tuned;
  a case that has not been re-solved does not ship in 2.0.
  `validation/crossval/manifest.json` and each case's committed artifact are
  the live source for a gate value; a number quoted in this table and not in
  the manifest is documentation, not the gate.

  Three groups of cases are controls and must come back unchanged: the
  boundary-PEC cases (`09`, `10`, `14`, `24`), the dielectric-only cases
  (`01`–`04`, `17`, `22`, `23`), and the σ-fill cases (`16`, `21`), whose metal
  is a conductivity written into cells rather than a declared conductor and is
  fenced out of the contract.
</Aside>

## Result codes

Each script returns one of these exit codes:

| Exit | Meaning |
|------|---------|
| `0` | Every self-check and numeric criterion passed, including each reference marked `required_for_script_pass` in the manifest. |
| `1` | A required run, self-check, or numeric criterion failed. |
| `2` | The rfx self-check completed, but a required external reference or optional dependency such as OpenEMS was unavailable. This result is inconclusive, not a pass. |

Some manifest entries also define a failure-line sentinel. The CPU runner
checks that sentinel after exit `0` and treats a contradictory failure message
as a failure.

## Cases not included

Research-only subgrid scripts are under `validation/research/subgrid/`. They are
not in the cross-validation manifest and are not documented as supported
reference cases.

## Reproduce the CPU subset

Run the CPU-feasible cases with:

```bash
PYTHONPATH=. python scripts/run_crossval_cpu.py
```

The runner starts each script in a fresh subprocess, applies a per-script
timeout, and prints one of these results:

| Result | Meaning |
|--------|---------|
| `PASS` | The script returned `0` and no failure sentinel was found. |
| `SELF-CHECK-ONLY` | The script returned `2`; required external evidence is unavailable, so the result is inconclusive. |
| `FAIL` | The script returned `1`, another unexpected exit code, or a contradictory failure sentinel. |
| `ENV-SKIP` | An optional reference solver such as Meep is installed but cannot be imported. This is an environment or packaging problem, not an rfx result. |
| `TIMEOUT` | The script exceeded its configured time limit. |

The runner exits `0` only when no script ends in `FAIL` or `TIMEOUT`.

Cases `03` and `04` require a Meep build compatible with the host NumPy ABI.
If Meep cannot be imported, the runner reports `ENV-SKIP` instead of `FAIL`;
case `04` still completes its rfx-side self-checks.
