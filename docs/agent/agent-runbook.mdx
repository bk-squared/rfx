# Agent runbook

Operational reference for agents working from a public clone: the exact
commands, validation lanes, and cadences. Current support authority lives in
the tracked `docs/guides/support_matrix.{md,json}` and
`docs/guides/sparameter_support_matrix.{md,json}` companions; this runbook
does not import rules or status from an untracked primary checkout.

Numbers here are checkable, not authoritative — where a live command is given, run it
rather than trusting the figure beside it.

## Test and lint

| what | command |
|---|---|
| test | `pytest` — live count: `python -m pytest --collect-only -q \| tail -1` |
| lint | `ruff check rfx/ tests/ --select E,F,W --ignore E501,F401,E741,E731,E701,E702,E402` |
| preflight | `sim.preflight()` — multi-check suite; grep `def _validate_` in `rfx/preflight/*.py` AND `rfx/api/_preflight.py` for the live set (the check families live in the package; the facade keeps the entry points and the request validators) |

Lint is gated in CI by `.github/workflows/lint.yml` on every push/PR. Note CI lints
`rfx/ tests/ validation/`; `scripts/` is out of scope.

### Adding a preflight check

The configuration checks are data, not a call list: `rfx/preflight/_registry.py` holds
`CORE_CONFIG_CHECKS`, and `_PreflightMixin._validate_simulation_config` builds the
shared context once and iterates it. So a new check is three steps in its own family
module and NO edit to `rfx/api/_preflight.py`: write the function with `self` first,
bind it on `_PreflightMixin` the way the other families do, then call
`register_config_check(ConfigCheck(name, adapter, family))` at module import. The
registry docstring carries the worked example.

Registration appends, and extras run after the whole core sequence — which is the
point, because `PreflightReport` preserves emission order and 65 committed reports in
`tests/locks/test_preflight_split_snapshot.py` pin it. A check that genuinely has to
speak earlier is a change to `CORE_CONFIG_CHECKS`, and reds both that lock and
`tests/locks/test_preflight_registry_sequence.py`, which pins the sequence and the
arguments each check receives. Neither red is one to regenerate past: it means
preflight output moved.

## PR body contract

Every PR body carries two lines, each exactly once, outside code fences and HTML
comments:

- `Lane: lane:<label>` — the owner lane, one of the repository's `lane:*` labels
  (`gh label list | grep '^lane:'`). Every open issue carries exactly one.
- `Review: <who read it> (separate instance) — ACCEPT` (or `ACCEPT WITH CHANGES`).
  A merged change is read by an agent instance other than the one that wrote it;
  several pods push under one GitHub account, so the body is the only provenance.
  `REJECT` never passes.

Two exceptions take `Review: skipped — <reason>`, and the reason must name which:
(a) an easily reverted pure docs/comment change, (b) an explicit instruction from
the PI to skip. Either dash, em or plain hyphen, is accepted.

The check is `scripts/ci/check_pr_body.py` (stdlib only; `--file PATH` to run it
against a body locally), gated by `.github/workflows/pr-body.yml` on open, edit,
reopen and synchronize. `.github/pull_request_template.md` seeds both stubs, and
`tests/contracts/test_pr_body_contract.py` pins the accepted forms.

## GPU validation

`scripts/vessl_gpu_suite.yaml` is THE maintained harness — runs `pytest -m gpu -q -ra`
on gpu-rtx4090:

```
vessl run create -f scripts/vessl_gpu_suite.yaml
```

**What it tests: `origin/main`, exported with `git archive` into a scratch dir** — NOT
the HEAD of the pod's primary checkout, and it never touches that checkout. Override
the ref with `RFX_GPU_SUITE_REF=<sha|branch>` in the run's `env` when validating a
branch. (Before 2026-09-15 the harness ran the primary checkout's HEAD as it stood;
a "post-merge" run then silently tested code 6 commits behind main — VESSL run
369367261080. The provenance block prints both the suite ref and the primary HEAD so
the log itself says what was tested.) Artifacts still land under the primary
checkout's `.omx/gpu-suite/<utc>-<short sha>/` on the shared volume.

**Cadence**: per release tag AND after any GPU-touching merge. Record pass/fail
counts in tracked release notes or a committed validation artifact suitable
for the claim.

One-off investigation YAMLs live in `scripts/archive/`. Do not resurrect them — write a
new YAML off the gpu_suite template.

The `distributed` pytest marker is declared but has zero tests; distributed coverage runs
in the fast suite via in-file XLA host-device sentinels.

## External cross-validation

Two lanes:

1. **Weekly CI** — `crossval-external` in `validation.yml`, conda-forge Meep.
   Exit-2 = visible SKIP, exit-1 = red.
2. **On-demand source-built openEMS** — `scripts/vessl_crossval_external.yaml`
   (cv05 + cv11) on the free `remilab-c0` cluster:
   ```
   vessl run create -f scripts/vessl_crossval_external.yaml
   ```
   Run it per release tag and after any change to the cv05/cv11 physics paths.

Historical environment notes and green-baseline logs that are absent from a
public clone are non-authoritative here. Treat the tracked harness, current
command result, support contracts, and committed artifacts as the available
evidence; do not infer a pass from unavailable history.

## Where the role fences live

Machine-readable crossval roles and registration live in
`validation/crossval/manifest.json`, contract-tested by
`tests/contracts/test_crossval_manifest_contract.py`. Current support status belongs in
the tracked support-matrix companions linked above, not in a private ledger.

The manifest covers `validation/crossval/*.py` only. Work outside that
directory is not a registered crossval lane; consult its tracked contract and
tests before making a support claim.
