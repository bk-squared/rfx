### Fixed — the `port_aperture_snap` preflight advisory now names what the port's cutoff is actually built from (#1101)

- On the API default `mode_profile="discrete"` the message said the solve
  builds its mode template *and cutoff* from the width `_range_to_slice`
  reports. It does not: `init_waveguide_port` takes `f_c` from the discrete
  eigenvalue of the realized aperture's own cell widths. Measured build-only on
  `validation/tmtt_paper/waveguide_dielectric_taper.py` (SMOKE, dx = 1 mm,
  declared WR-90): declared-width analytic 6.557140 GHz, realized-aperture
  analytic 6.517227 GHz, built `cfg.f_cutoff` 6.512162 GHz.
- The row now reads the built `cfg.f_cutoff` off the same port config the run
  builds, names the mode and the profile it came from, says that the declared
  widths still select which eigenvalue is taken, and quotes both analytic
  values so a reader can check it without rebuilding the port.
- The discrete mode solve is a dense eigendecomposition of an `(nu*nv, nu*nv)`
  matrix, so the check builds nothing above
  `WAVEGUIDE_PREFLIGHT_DISCRETE_CELL_BUDGET` (2000 transverse cells) and quotes
  the analytic cutoff of the realized aperture there instead, labelled as such.
  Without that bound a two-port WR-90 `preflight()` at dx = 0.125 mm cost 127 s
  and 10.7 GB.
- The transverse spans and the cell counts the row quotes are read from
  each axis' own cell size (`getattr(grid, "dy", grid.dx)`) rather than
  from `dx`, and the row names the size it used. The uniform `Grid` carries
  only `dx`, so nothing moves numerically on any grid this check runs on.
- The declared-vs-rasterized half of the message is unchanged.
